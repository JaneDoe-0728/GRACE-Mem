## 一、預設路徑的靜默檢索失效

**症狀。** `readme.md` 裡印出來的 Retriever 範例，回傳的是字串 `"(no KG context)"`。

**成因。** [`evidence.py:545`](../KG/pipeline/retrieval_steps/evidence.py#L545) 呼叫：

```python
snippet = self.summaries_vdb.get_summary_text_by_id(summary_id, full=True)
except AttributeError:
```

但 [`SummariesVDB.get_summary_text_by_id`](../KG/storage/chroma_vdb.py#L481) 只接受
`summary_id`。因此丟出的是 **`TypeError`**，它躲過了 `except AttributeError`，一路往上
拋，最後被 `build_kg_context` 的大範圍 handler 接住，回傳
[`"(no KG context)"`](../KG/pipeline/retriever.py#L2459)。呼叫點沒有任何記錄，所以這個
失效是看不見的。

重現時 `logs/kg_retriever.jsonl` 的實際證據：

```
context_build_done      {'entity_count': 2, 'relationship_count': 1, 'has_context': True}
build_kg_context_failed {'error': "...get_summary_text_by_id() got an unexpected keyword argument 'full'"}
```

context 組裝其實**成功了**，炸掉的只有 evidence 步驟。

**修法。** 拿掉多餘的 kwarg，並把 except 放寬為 `(AttributeError, TypeError)`。

**影響範圍。** 實驗管線不受影響，因為 `experiment_config.py` 設了
`use_split_embeddings=True`，會走 `_build_evidence_split`，那條路上的呼叫是正確的。只有
使用 `build_pipeline()` 預設值的人 —— 也就是照著 readme 操作的人 —— 會踩到。

### 預設設定重新對齊

`RetrieverConfig` 現在預設 `use_split_embeddings=True` 與
`split_single_entry_raw=True`，讓 `build_pipeline()` 走上與 benchmark 相同的 evidence
路徑。

這兩個旗標**必須**一起動。split 路徑把 entry id 解析成 `{summary_id}{suffix}`；當
`split_single_entry_raw=False` 時後綴是 `:u` / `:a`，而 `Ingestor` 從來不會寫出這種
entry。只翻 `use_split_embeddings` 的話，等於用一個靜默失效換掉另一個。

`RetrieverConfig(**RERANKER_PARAMS)` 是**整份取代**而非合併，所以更動 dataclass 預設值
確實會外溢到實驗管線中所有 `RERANKER_PARAMS` 沒列出的欄位。這次動到的兩個 key 在那裡都
有明確設定，因此管線不受影響 —— 這是動手前先查證過的。

## 二、LongMem 的 split summary 從來沒有被建立過

**症狀。** 沒有任何症狀。問題正在於此。

**成因。** `rebuild_split_summaries.py` 只出現在註解裡 —— **程式碼中沒有任何地方呼叫
它**。與此同時 `processor.py` 把 `split_single_entry_raw=False` 寫死，於是檢索去查
`{sid}:u` / `{sid}:a`，而全新的 ingest 根本不會寫出這些 entry。

後果是「部分失效」，這正是它一直沒被發現的原因：所有 provenance 候選的分數都是 `None`
因而被丟棄，但 direct-vector 通道（`summary_direct_vector_topn=50`）仍持續回傳真實
entry。於是檢索退化成單純的向量搜尋、整個 KG/provenance 通道形同死亡，而且不拋出任何
錯誤。

**修法。** `INGEST_PARAMS["use_split_summary"]`（預設 `True`）現在同時驅動**兩邊**：

| | ingest 後的 rebuild | 檢索旗標 |
|---|---|---|
| `use_split_summary=True` | 執行 | `split_single_entry_raw=False` |
| `use_split_summary=False` | 略過 | `split_single_entry_raw=True` |

因為由單一旗標決定兩者，artifact 佈局與檢索設定不可能各說各話。`processor.py` 和
`rerun.py` 都不再寫死該旗標，並且有測試會擋下任何重新引入字面值的修改。

rebuild 掛在 [`processor.py:837`](../experiment/longmem/processor.py#L837)，也就是
`turn_pairs` 與 `session` 兩種 ingest 模式唯一的匯流點。它直接呼叫 `rebuild_artifact()`
而非 shell out 到 CLI，而且是冪等的 —— 已有 `summaries_chroma_bak` 備份的 artifact 目錄
會被跳過 —— 所以續跑與重跑都安全。`RawContextLookup` 與 llmlingua compressor 只建立一次
並跨 dataset 重用，且刻意不被 `_cleanup_current_dataset()` 清除。

## 三、LoCoMo 分塊 ingest

分塊功能本來就存在，但實際上幾乎無法使用：由 `LOCOMO_CHUNK_TURNS` 環境變數驅動、在
import 時讀進模組常數、預設值為 `0`、不存在於 `experiment_config.py`、也沒有任何文件。
整個 repo 中沒有任何腳本或文件曾經設定過它。

**變更內容。**

- `INGEST_PARAMS["chunk_turns"] = 8` 成為唯一真實來源，並以 `--chunk-turns` 對外開放。
- 環境變數移除。它與 readme 宣稱「`experiment_config.py` 是唯一真實來源」直接衝突，而且
  會無聲地凌駕其上。
- `_iter_dialogue_chunks` 改為接受明確參數，不再讀模組常數。import 時凍結的常數無法讓
  orchestrator、各個 worker 子行程與 snapshot builder 帶不同的值，也無法測試。

**參數流向**

```
INGEST_PARAMS["chunk_turns"]
  → cli.py --chunk-turns → args
  → workers.py → stage_adapter.run_ingest_stage_for_{locomo,records}
  → sessions_to_one_turn_df / session_records_to_df
  → _iter_dialogue_chunks
```

五個呼叫點全部都有傳。其中
[`snapshot.py:310`](../experiment/locomo/snapshot.py#L310) 最關鍵也最容易漏掉：這裡若不
一致，每一個 `summary_id` 都會位移，還原出來的 artifact 就與產生它的那次 run 對不上，而且
是靜默發生的。

**行為變更須知。** `summary_id` 由固定的 `:0` 變成 `:{chunk_index}`。先前 run 產生的
artifact 屬於不同粒度；透過 `--artifact-dir` 沿用時取得的仍是整 session 粒度。
`--chunk-turns 0` 可重現先前行為。

**一處刻意保留的不對稱。** `chunk_turns > 0` 時空 dialogue 不會產生任何 chunk，因此不會
寫出 summary；`chunk_turns <= 0` 則會產生一個空 chunk。這個差異被保留下來：`chunk_turns=0`
的存在意義就是逐位元重現舊 run，所以它的行為是凍結的；而分塊模式跳過空 session，本來就
比往 VDB 寫進一筆空 entry 來得好。兩個分支都有測試釘住。

**未變更的部分。** `summary_direct_vector_topn=50`、`summary_rerank_topk=16` 與
`_RERANK_POOL_CAP=40` 是照整 session 粒度調出來的。分塊會讓候選池變大，因此這些值值得
重新 sweep —— 這點寫進了 `experiment_config.py` 與 `experiment/readme.md`，而不是我憑
推測去改。

## 四、`VDBManager` 的巢狀 artifact 路徑

`VDBManager.__init__` 呼叫 `self.ART.mkdir(exist_ok=True)` 卻沒有帶 `parents=True`，因此
`VDBManager(Path("a/b/c"))` 在 `a/b` 不存在時會丟 `FileNotFoundError`。實務上沒踩到，是
因為管線都會先呼叫 `ensure_dir()`。已修正。

## 五、文件對照程式碼的修正

以下每一項都是實際執行或閱讀程式碼驗證過的，不是靠推論。

**模組佈局 / API 參考**

| readme 寫的 | 實際 |

**ChromaVDB 那一節整節都是錯的** —— 它描述的是 chromadb 自己的 API，而不是這個 wrapper。
類別名稱是 `SimpleChromaVDB`；它吃的是預先算好的向量而非文字，且每一列的 id 是從
metadata 讀取：

| 文件寫的 | 實際 |
|---|---|
| `add(texts, metas, ids)` | `add(vectors: np.ndarray, metadatas)` |
| `query(query_texts, n_results, where, ...)` | `search(query_vec, top_k, threshold)` |

（只有 `_V2` 存在），以及 `_validate_entity_ops_output`（在 `llm/client.py` 裡是被註解
掉的）。

**ID 格式原本也是錯的。** `canonical_entity_id("AI Workshop", "Event")` 回傳
`event_ai_workshop`，不是 `type::name`；`canonical_rel_id` 用 `_` 串接，不是 `::`。

**Setup 章節**

- submodule 指示已移除。沒有 `.gitmodules`；`noco-db-uploader` 是以 11 個一般追蹤檔案的
  形式 vendored 進來的，所以 `--recurse-submodules` 是 no-op，只會讓人誤以為漏抓了東西。
- `docker-compose.yml` 定義的是**四個** FalkorDB 服務（6379–6382 / UI 3000–3003），不是
  一個。已如實記載，並針對常見情況給出 `up -d falkordb`。
- **新增章節：取得 benchmark 資料。** 兩個資料目錄都被 gitignore，所以全新 clone 無法執行

  LongMem CSV schema —— `session_id`、`turn_index`、`role`、`content`、
  `dialogue_datetime`、`question`，選用的 `answer` / `question_date`。文件中也明確指出這個

  腳本**。官方下載網址刻意留白：在這裡無法驗證，而寫錯的網址比明顯的空缺更糟。

## 六、`setup_env.sh`

原本在 `set -euo pipefail` 之下無條件使用 `sudo docker`，因此在沒有 sudo 的機器或非互動
shell 中會直接中斷。現在改為：能直接存取 daemon 時優先用純 `docker`，必要時才退回 sudo，
兩者皆不可用時以明確訊息結束，並指出替代作法（把 `NEO4J_URI` 指向現有的 FalkorDB 並跳過
此腳本）。同時只啟動主要的 `falkordb` 服務，而不是四個一起拉起來。

## 七、測試

新增兩個檔案，都是自給自足的，在服務不存在時會乾淨地跳過：

- **`test/test_readme_claims.py`** —— 釘住 readme 的每一項宣稱：模組佈局、API 符號與簽名、
  CLI flag、`.env.example`、`setup_env.sh` 步驟順序、docker-compose、lockfile 是否同步、
  以及沒有寫死 IP。另有 6 個整合測試，會對著實際運作的環境逐字執行 readme 裡的兩個
  Python 範例。
- **`test/test_chunk_and_split_config.py`** —— 釘住分塊行為與 split-summary 的耦合，包含
  「每個呼叫點都有轉傳 `chunk_turns`」以及「兩個 LongMem 檔案都沒有寫死
  `split_single_entry_raw`」這兩道防漏測試。

兩個 regression 都做過紅綠驗證：把修正還原後，相關測試會以原本的錯誤訊息變紅；恢復後
整組轉綠。

**既有測試套件的修復**（原本 12 個失敗）：

| 測試 | 處置 | 理由 |
|---|---|---|
| `test_chroma_manager_paths`（1 個） | 修**程式** | 真的是 `parents=True` 的 bug |
| `test_keyword_prompt`（2 個） | 修**測試** | prompt 新增了 `{guidance_section}`，呼叫端有正確傳入，production 沒問題 |
| `test_query_time_parser`（6 個） | 修**測試** | 見下方說明 |
| `test_query_time_parser`（3 個） | `xfail(strict=True)` | temporal core 確實偵測不到的表達式 |

那 6 個改寫格式的測試選擇更新為現行行為、而不是改實作，原因是 `rewrite_temporal_text`
同時也會改寫 ingest 時存入的 summary 文字 —— 更動它會讓既有 artifact 與新 run 不再可比。
這些測試現在額外斷言完整區間仍可透過 `normalized_start` / `normalized_end` 取得，因此
即使表層形式是短語，資訊沒有遺失這件事也被證明釘住了。

`two weekends ago`、`two fortnights ago` 與 `last quarter` 產生的 `constraints` 是空
list —— 它們根本沒被偵測到。這裡選擇標記 `xfail(strict=True)`，而不是改寫成「斷言它不
支援」，這樣一旦有人實作了其中任何一個，測試會變成 XPASS 並提醒更新。

`pyproject.toml` 加入了 `integration` 與 `slow` 兩個 marker 的註冊，避免這兩個被 commit
的測試檔每次執行都噴出 unknown-marker 警告。

**結果：** 253 passed、6 skipped、3 xfailed。

`test/test_compress.py` 不計入上述數字 —— 它硬性需要 CUDA，而當時 GPU 幾乎滿載。等 GPU
空下來後值得單獨執行一次。
